# License Auditor - райтап

Категория: Reverse Engineering. Технология: Go-бинарник (ELF 64-bit, statically linked, stripped). Инструменты: `file`, `strings`, `checksec`, Ghidra, Python.

Флаг: `flag{go_license_auditor_accepts_the_right_key}`

Конспект решения сверху вниз: не только что я нажимал, но и почему, плюс честный разбор тупиков по дороге. Задача учебная, но хорошо показывает, чем Go-реверс отличается от обычного C и где на этом легко споткнуться.

## Условие

Внутренняя CLI-утилита проверяет лицензии для учебного SOC-портала. Обычно она печатает краткий отчёт: продуктовую линейку, уровень лицензии, количество мест, срок действия. В легенде сказано: после миграции кто-то оставил в бинарнике диагностический режим для валидной подписи. Вокруг двух слов, диагностический режим и валидная подпись, и крутится весь таск.

## Разведка

С любым незнакомым бинарём начинаю с трёх команд:

```bash
file ./license_auditor
strings ./license_auditor
checksec --file=license_auditor
```

`file` показал `ELF 64-bit LSB executable, x86-64, statically linked, stripped`. `statically linked` значит все библиотеки внутри, внешних зависимостей нет. `stripped` значит нет отладочной информации (DWARF: имена переменных, типы, номера строк). Для обычного C это был бы серьёзный удар по реверсу.

Хвост `strings` выдал интересное:

```text
.gopclntab
.go.buildinfo
.go.fuzzcntrs
.go.fipsinfo
.typelink .itablink .gosymtab
```

Секции с префиксом `.go*`, и особенно `.gopclntab` (program counter line table), это подпись компилятора Go. Ни C, ни C++, ни Rust таких секций не делают. И вот почему это отличная новость даже при `stripped`: секция `.gopclntab` нужна самому рантайму Go для стектрейсов и паник, её почти никогда не вырезают, а внутри неё лежат имена функций. То есть для Go слово «stripped» значит гораздо меньше, чем для C: имена функций можно восстановить.

`checksec` показал `No RELRO`, `No canary`, `NX enabled`, `No PIE`. Для реверса это не критично (это защиты из мира pwn), но на заметку взял.

Запуск вживую:

```text
$ ./license_auditor
license key: 8whOHzEFBhCsTEtMm101/0fU_2xC3aZJgmMKMAlhG/cZ7xY2AMEw0D3t0ldoTW/eA7mlobVSAbjfusZVVdc
license-auditor: malformed license key
expected format: LIC-XXXXX-XXXXX-XXXXX-XXXXX
```

Отсюда два факта. Программа печатает какой-то дефолтный `license key`, длинную строку `8whOHz...` из букв обоих регистров, цифр, `_` и `-`. И требует формат `LIC-XXXXX-XXXXX-XXXXX-XXXXX`.

## Восстанавливаем имена функций в Ghidra

Первый тупик: спутал строку-имя с самой функцией. Загрузил бинарь в Ghidra, через Search Text искал `main.main`. Нашлось две записи:

```text
0x00499000   main.main             сама функция (адрес в .text, Preview: Golang stacktrace signature)
0x005615b8   main.main___fun...    запись-метка в .gopclntab (main.main@0x00499000)
```

Урок простой: строка `"main.main"` в `.gopclntab` это просто текстовая метка «тут живёт функция», а сама функция это машинный код в `.text`. Разные вещи. Ghidra с Go-анализом не только нашла метку, но и привязала её к коду.

Главный вывод отсюда: раз `main.main` опознана по имени, то и остальные `main.*` функции тоже получили имена. Это и есть тот клад, ради которого стоило лезть в секции. Фильтрую окно Functions по `main.` и работаю только со своими, авторскими функциями, игнорируя тысячи функций рантайма.

## Ищем точку входа через строки

Второй тупик: `Defined Strings` в Go почти бесполезен. Я хотел пойти от видимого вывода к коду: нашёл строку на экране, нашёл её в бинаре, посмотрел, кто на неё ссылается через XREF, и попал в нужную функцию. Нормальный подход для C. Но фильтр `malformed` в Defined Strings выдал только строки рантайма (`runtime: malformed profBuf...`, `malformed GOMEMLIMIT...`), а строки `malformed license key` там не было вообще.

Причина в том, как Go хранит строки. Все строки программы лежат одним непрерывным блоком байт без нулевых разделителей. Обычные C-строки заканчиваются `\0`, и Ghidra режет текст по этим нулям. В Go нулей между строками нет, вместо этого есть отдельная таблица вида «строка номер такой-то это байты с X по Y». Поэтому автоанализ видит один гигантский слипшийся кусок и не умеет нарезать его на отдельные строки.

Проверка в терминале это подтвердила:

```bash
strings ./license_auditor | grep -i "malformed license"
# ...license-auditor: malformed license key1110223024625156504236...
```

Видно, что `malformed license key` без всякого разделителя переходит прямо в цифры `1110223...`. Текст в бинаре есть, просто Ghidra его не выделила.

Правильный путь для Go это Search Memory, поиск по сырым байтам. `Search -> Memory...` в режиме String ищет текст прямо в байтах всего бинаря, даже если Defined Strings его не разложил.

Слово для поиска выбираю от условия. «Диагностика» это `diag` (или `debug`, `dev`), «подпись» это `sign` или `signature`, «отчёт» это `report`. Ищу именно интересную ветку, а не обработчик ошибки `malformed`. Поиск `diag` привёл к золоту:

```text
s_diagnostic_flag:_%s_004bf8a6    XREF[1]: main.main:0049915a
char[20]   "diagnostic flag: %s\n"
```

Строка `diagnostic flag: %s\n` это и есть тот самый диагностический режим, а `%s` это плейсхолдер, куда программа подставит значение. XREF ведёт в `main.main:0x49915a`, то есть печатает её именно `main.main`.

## Логика main.main

Двойной клик по XREF, и я в `main.main`. Ключевой псевдокод (строки 53–86 декомпиляции):

```c
main.readInput();
main.parseLicense();
...
if (extraout_R10 == 0) {                                 // парсинг прошёл?
    main.printReport(...);                               // обычный краткий отчёт
    cVar1 = main.validSignature(extraout_RSI, R8, R9);   // проверка подписи
    if (cVar1 != '\0') {                                 // если подпись валидна
        ...
        sVar4 = (string)main.openSeal(extraout_RSI, R8, R9); // расшифровка флага
        ...
        sVar4.str = "diagnostic flag: %s\n";             // печать флага
        fmt.Fprintf(w_00, sVar4, a_03);
    }
}
```

Если убрать детали, картина такая:

```text
if (подпись валидна) {
    напечатать "diagnostic flag: <СЕКРЕТ>"
}
```

Условие победы: диагностический режим включается только тогда, когда `main.validSignature` вернёт true для моего ключа.

## Почему патчить проверку бесполезно

Третий тупик был соблазнительным: а давай просто занопим `if (cVar1 != '\0')`, чтобы программа всегда заходила в диагностическую ветку. Идея напрашивается сама, но я заглянул в `main.openSeal`, и она отвалилась:

```c
// main.openSeal(int param_1, uint param_2)
dVar2 = 0x9e3779b9;                        // стартовая константа (золотое сечение)
for (iVar1 = 0; iVar1 < param_2; iVar1++) {
    dVar2 = dVar2 ^ (*(iStack + iVar1*8) + 1) * (iVar1 + 0x45d9f3b);
    dVar2 = (dVar2 << 7 | dVar2 >> 0x19) + 0x6d2b79f5;   // rotate + add
}
...
local_36 = _DAT_00562620;                  // зашитый зашифрованный флаг
```

Разница между проверкой и расшифровкой тут решает всё. `validSignature` только проверяет, возвращает 0 или 1, и её действительно можно обмануть патчем. А `openSeal` использует байты ключа как материал для расшифровки флага, крутит их через самодельный поточный шифр (константа `0x9e3779b9` это частый маркер таких хешей и PRNG). Поэтому если занопить `validSignature`, программа-то в ветку войдёт, но `openSeal` получит неправильные байты и расшифрует мусор вместо флага. Нужен настоящий валидный ключ, причём нужен он не проверке (её можно обойти), а расшифровке (её обойти нельзя, она математически завязана на правильные байты).

Задача превратилась из «обойти проверку» в «найти ключ, который проходит `validSignature`».

## Формат ключа: parseLicense

Разбираю, во что превращается ключ `LIC-XXXXX-XXXXX-XXXXX-XXXXX`:

```c
sVar17 = strings.TrimSpace(sVar17);    // убрать пробелы
sVar17 = strings.ToUpper(sVar17);      // всё в верхний регистр
sep.str = "-";
genSplit(sVar17, sep, ...);            // разрезать по "-"
if (psVar4->len == 5 && *str == 0x494c && str[2]=='C') // 5 групп, первая = "LIC"
...
if (psVar4[1].len != 5) break;         // каждая группа ровно 5 символов, иначе "bad group length"
...
s_00.str = "ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789";   // алфавит из 36 символов
iVar7 = strings.IndexRune(s_00, symbol);             // позиция символа в алфавите (0-35)
if (iVar7 < 0) break;                                // нет в алфавите, "bad alphabet"
```

Это кодировка base36. Алфавит из 36 символов (`A-Z` плюс `0-9`), `IndexRune` превращает каждый символ в число от 0 до 35. То есть ключ это по сути число, записанное 36 «цифрами».

Весь разбор ключа по шагам: `TrimSpace` и `ToUpper` (отсюда регистронезависимость), режется по `-`, ждёт 5 групп, первая должна быть `LIC`, каждая из 4 оставшихся групп это 5 символов, итого 20 символов base36, и каждый символ превращается в число 0–35 и складывается в массив `KEY[]`.

Любопытная деталь: почему ввод в base36, а хранимый дефолтный ключ в base64. Дефолтный `8whOHz...` содержит `_`, `-` и оба регистра, это base64url с его 64 символами. А ввод `LIC-...` это base36. Разница не случайная. base36 удобен человеку: регистронезависим, нет путающих спецсимволов, группы по 5 как серийник Windows, легко набирать руками. base64 компактнее, но регистрозависим и со спецсимволами, человеку неудобен, зато хорош для хранения. Это инженерное решение под сценарий, а не запутывание ради запутывания.

Важная проверка: все ли значения `KEY[]` не больше 35? Да, максимум 34, байт больше 35 нет. Значит ключ это ровно 20 чисел base36 напрямую, без позиционного умножения, и закодировать обратно будет тривиально.

## Сердце таска: validSignature

Тут два слоя проверки одних и тех же 20 байт `KEY[]`:

```c
// слой 1: две контрольные суммы
iVar5 = 0;
for (i=0; i<param_2; i++) iVar5 += (i+3) * KEY[i];       // взвешенная сумма

sVar4 = 0x4d3a;
for (i=0; i<param_2; i++) { ... XOR, сдвиги ...; sVar4 = ... + 0x1337; }

if (iVar5 % 0x3e5 == 0x53 && sVar4 == 0xb0f1) {          // 997 -> 83, и == 45297
    // слой 2: 20 побайтовых сверок
    duffcopy(local_a8, &DAT_00562a40);                   // эталон-индексы
    sVar4 = -0x5a6f11e4;                                 // старт LCG
    while (true) {
        if (0x13 < iVar2) return 1;                      // прошли 20, валидно
        uVar1 = local_a8[iVar2];                         // idx из DAT_00562a40
        if (param_2 <= uVar1) break;
        sVar4 = sVar4 * 0x19660d + 0x3c6ef35f;           // шаг LCG
        if (DAT_00562380[iVar2] !=
            (byte)(iVar2 * '\v' + '\x05' + KEY[uVar1]) ^ (byte)(sVar4 >> 0x10))
            return 0;                                     // не сошлось, невалидно
        iVar2++;
    }
}
```

Главная удача тут это LCG, линейный конгруэнтный генератор. Строка `sVar4 = sVar4 * 0x19660d + 0x3c6ef35f` это простейший генератор псевдослучайных чисел: новое равно старое умножить на A плюс C. Он полностью детерминирован: стартует с фиксированного `-0x5a6f11e4` и считается одинаково при каждом запуске, от ключа никак не зависит. Вот почему это критично. Раз LCG известен заранее, то в формуле проверки единственное неизвестное это `KEY[uVar1]`. Если бы LCG зависел от ключа, был бы замкнутый круг (чтобы найти байт, нужен LCG, а LCG зависит от байта), и пришлось бы решать через z3 или перебор. А так байт вычисляется напрямую.

Если упростить формулу проверки, получается вот что:

```text
DAT_00562380[i] == (i*11 + 5 + KEY[idx]) ^ (lcg >> 16)
```

где `idx = DAT_00562a40[i]`. Константы: `'\v'` это 11, `'\x05'` это 5, `>>0x10` это `>>16`.

Теперь обращаю формулу. Единственное неизвестное это `KEY[idx]`, значит перебор не нужен, байт считается. Сначала убираю XOR (из `C == X ^ L` следует `X == C ^ L`), потом убираю сложение, перенося `(i*11+5)` вправо со знаком минус:

```text
KEY[idx] = (DAT_00562380[i] ^ (lcg>>16)) - (i*11 + 5)       (всё & 0xFF)
```

Четвёртый тупик был как раз здесь: я сначала обратил формулу неправильно. Первая попытка выглядела как `KEY[idx] = (i*11 + 5 + DAT) ^ (lcg>>16)`, но это просто переписанная исходная формула, где `KEY` так и остался заперт внутри сложения. Правильно наоборот: сначала XOR применяется к `DAT`, и только потом вычитается `(i*11+5)`.

Почему вообще не брутфорсить все 20 байт сразу: `256^13` это примерно `10^31` вариантов, тут и вселенной не хватит. А прямое вычисление мгновенно.

## Вытаскиваем эталонные массивы

Пятый тупик, важный для Go: массивы бывают с разным размером элемента, и каждый надо проверять на тип отдельно.

`DAT_00562a40` имеет тип `uint`, а значит 8 байт на элемент (на 64-битной машине). Значения стоят через каждые 8 байт, между ними нули:

```text
idx = [07,02,0f,00,0b,13,05,0d,08,01,11,04,0a,10,03,0e,06,12,09,0c]   # каждый 8-й байт
```

Если бы я взял «подряд 20 байт», получил бы кашу из нулей. Кстати, это перестановка чисел от 0 до 19, каждое ровно один раз, а значит все 20 байт ключа задаются ровно по одному, никаких недоопределённых байт нет, и z3 не нужен.

`DAT_00562380` имеет тип `undefined1`, то есть 1 байт на элемент, значения идут подряд:

```text
dat = [41,be,40,14,e6,a1,b3,d0,cd,16,3c,01,b1,cb,b2,ed,4c,52,31,4b]
```

Хвост `4c 52 31 4b` это ASCII `L R 1 K`, то есть читаемо, значит это не случайный мусор. Урок на будущее: `undefined8`, `uint`, `long` это 8 байт на элемент (значения через 8, с нулями между ними), а `undefined1`, `byte`, `char` это 1 байт на элемент (подряд). Нельзя переносить вывод с одного массива на другой по аналогии, тип надо смотреть в Ghidra для каждого отдельно.

## Решатель на Python

```python
idx = [0x07,0x02,0x0f,0x00,0x0b,0x13,0x05,0x0d,0x08,0x01,0x11,0x04,0x0a,0x10,0x03,0x0e,0x06,0x12,0x09,0x0c]
dat = [0x41,0xbe,0x40,0x14,0xe6,0xa1,0xb3,0xd0,0xcd,0x16,0x3c,0x01,0xb1,0xcb,0xb2,0xed,0x4c,0x52,0x31,0x4b]

lcg = (-0x5a6f11e4) & 0xffffffff
key = [0x00] * 20

for i in range(20):
    lcg = (lcg * 0x19660d + 0x3c6ef35f) & 0xffffffff   # обновить LCG (32 бита)
    k = (dat[i] ^ (lcg >> 16)) - (i * 11 + 5)          # обратная формула
    key[idx[i]] = k & 0xff                             # писать по idx, не по i

print(bytes(key))

# самопроверка чексуммой слоя 1
iVar5 = sum((i + 3) * key[i] for i in range(20))
print("checksum1:", iVar5 % 997, "(надо 83)")
```

Тупики уже в самом коде решателя:

- Приоритет операций. Первая версия строки LCG была `lcg * 0x19660d + 0x3c6ef35f & 0xffffffff`. В Python `&` имеет приоритет ниже, чем `+`, поэтому это читалось как `lcg*A + (C & 0xffffffff)`, и обрезка до 32 бит не применялась ко всему выражению, LCG рос без ограничения. Лечится скобками: `(lcg * 0x19660d + 0x3c6ef35f) & 0xffffffff`. В Python и в C/Go приоритеты битовых и арифметических операций разные, так что когда мешаешь `&`, `+`, `>>`, скобки лучше ставить явно.
- Порядок действий. LCG надо обновлять перед вычислением байта, ровно как в коде: строка `sVar4 = ...` стоит перед сравнением.
- Разрядность. `sVar4` это 32-битное знаковое, поэтому обязательно `& 0xFFFFFFFF`, иначе Python со своими безразмерными int посчитает неверно.

Самопроверка выдала `checksum1: 83`, что и требовалось. То есть байты правильные, несмотря на мусорный вид. Смысл этой проверки вот в чём: слой 1 (чексуммы) я не решаю, байты из него не вычисляю, но использую его как подстановку корня обратно. Прогоняю восстановленный ключ через чексумму, и если `iVar5 % 997 == 83`, значит байты точно верные. Это ловит ошибки в LCG, разрядности и индексах ещё до того, как я потрачу время на запуск программы.

Восстановленные байты все оказались не больше 35, то есть это и есть 20 цифр base36.

## Короткая выжимка

- Как опознал Go: секции `.gopclntab` и `.go.*` в `strings`. Для Go «stripped» не равно потере имён функций, `.gopclntab` держит имена, и Ghidra их восстанавливает.
- Почему строки не нашлись в Defined Strings: Go склеивает все строки в один блок без `\0`-разделителей. Решение это Search Memory по сырым байтам.
- Почему нельзя было занопить проверку: `validSignature` проверяет (обходима), но `openSeal` расшифровывает флаг теми же байтами ключа. Патч проверки даёт мусор вместо флага, нужен настоящий ключ.
- Что такое LCG и почему помог: детерминированный генератор, от ключа не зависит, поэтому в формуле проверки единственное неизвестное это байт ключа, и он вычисляется напрямую, без перебора.
- Как восстановил ключ: обратил формулу `KEY[idx] = (dat[i] ^ (lcg>>16)) - (i*11+5)`, прогнал LCG, собрал 20 чисел base36, закодировал в `LIC-...`.
- Главная ловушка Go-массивов: `uint` это 8 байт на элемент (через 8, с нулями), `undefined1` это 1 байт (подряд). Тип смотреть в Ghidra для каждого массива.
