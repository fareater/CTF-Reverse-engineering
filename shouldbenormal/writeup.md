# ShouldBeNormal (ALittlePatate) - райтап

Крякми: <https://crackmes.one/crackme/6a74ea7f05a9e80a907242b9>

Linux ELF x86-64, внутри самописный пакер и байткодная VM. Если открыть в дизассемблере как есть, увидите в основном мусор, потому что нормальный код появляется только в рантайме и крутится внутри VM.

Сразу спойлер: пароль автора `transrights`. Но проверяется только 32-битный хеш от 11 символов, так что подходит любая строка с таким же хешем, например `wolffmumify` или `treelyinbke`.

## Первый запуск

Пароль от архива стандартный для сайта, `crackmes.one`.

```bash
$ file ShouldBeNormal
ShouldBeNormal: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), dynamically linked, \
interpreter /lib64/ld-linux-x86-64.so.2, not stripped

$ sha256sum ShouldBeNormal
189ccd87ccc10daa98ee3f695a9b11aa458cf3e123df402a93d2dce3cfdebcdc  ShouldBeNormal
```

Пароль передается первым аргументом:

```bash
$ ./ShouldBeNormal
usage: ./ShouldBeNormal password

$ ./ShouldBeNormal wrong
bad password.

$ ./ShouldBeNormal transrights
good job!
```

Смотрим readelf:

```text
Entry point address: 0x424ae0

 .text       address 0x401090, size 0x1b0
 .rodata     address 0x402000, size 0x30
 .patate     address 0x405000, size 0x60468, flags WAX
```

В `.text` всего 432 байта стандартного CRT-обвеса. Все остальное (~386 KB) лежит в секции `.patate` с флагами WAX, и entry point смотрит прямо туда. `_start` при этом на месте, по `0x401090`, но стартует программа не с него. Строки в `.rodata` на диске нечитаемые. В общем, понятно, что это пакер, и дизасм "в лоб" ничего не даст.

## Статика

`_start` выглядит обычно и зовет `__libc_start_main`:

```asm
0x401090: xor    ebp,ebp
0x401099: pop    rsi
0x40109a: mov    rdx,rsp
...
0x4010a8: mov    rdi,0x4011df
0x4010af: call   [__libc_start_main@GOT]
```

А вот `main` по `0x4011df` оказывается просто прыжком:

```asm
0x4011df: endbr64
0x4011e3: jmp    0x41515d
```

По `0x41515d` в файле нули и мусор. Значит, кто-то расшифровывает туда код до того, как управление дойдет до main.

Кто именно, видно в `.dynamic`:

```text
DT_INIT       0x405850
DT_INIT_ARRAY 0x403df8
```

Обычно `DT_INIT` указывает на `.init` (где-то в районе `0x401000`), а тут он ведет в `.patate`. Загрузчик вызывает `DT_INIT` раньше main, вот там и сидит часть распаковки. Я на этом сначала споткнулся: в своем эмуляторе сразу прыгнул из `__libc_start_main` в main, и, естественно, ничего не расшифровалось.

## Антиотладка

strace сразу показывает, в чем дело:

```text
open("/proc/self/status", O_RDONLY) = 3
read(3, "Name:\tShouldBeNormal\n...", 1024) = 1024
exit(1) = ?
```

Читается `TracerPid` из `/proc/self/status`. Под strace или gdb там не ноль, и программа тихо выходит, даже не дойдя до проверки. В обычном запуске `/proc/self/status` открывается два раза.

Ничего сложного, но отлаживать пошагово неудобно. Поэтому я дальше работал в Unicorn: подсовываю программе фейковый status с `TracerPid: 0`, и заодно можно логировать каждый адрес и каждое обращение VM к своим регистрам.

## Эмулятор

Что пришлось реализовать:

1. Замапить `PT_LOAD` по их адресам.
2. Собрать начальный стек по System V: argc, argv, envp, auxv.
3. Перехватить через GOT `strlen`, `puts`, `__fprintf_chk` и `__libc_start_main`.
4. Сисколы `mprotect`, `open`, `read`, `close`, `exit`.
5. На старте вызвать `DT_INIT` (`0x405850`) и только потом трамплин main (`0x4011df`).
6. На открытие `/proc/self/status` отдавать содержимое без трейсера.

Два места, на которых я потерял время.

Первое: я копировал в память только `p_filesz` байт каждого сегмента. Ядро так не делает, оно мапит файл страницами, и в хвосте страницы оказываются данные из файла за пределами сегмента. Здесь это важно, потому что есть два соседних сегмента:

```text
PT_LOAD vaddr=0x402000 filesz=0x138 offset=0x2000
PT_LOAD vaddr=0x403df8 filesz=0x230 offset=0x2df8
```

Один и тот же кусок файла виден через обе страницы. При копировании "впритык" таблица, по которой распаковщик ищет зашифрованные строки, у меня была забита нулями, и расшифровка шла не так, как в реальном процессе.

Второе: про `DT_INIT` выше уже написал. Именно там меняются права страниц и стартует расшифровка. Когда исправил оба пункта, память эмулятора совпала с живым процессом, и строки с VM заработали.

## Расшифровка и VM

После старта `.patate` перезаписывается прямо в памяти. Цикл такой:

```asm
movzx eax, byte ptr [rsi]
movzx r9d, al
xor   al, dl
mov   byte ptr [rsi], al
imul  edx, edx, 0x41c64e6d
add   edx, r9d
add   edx, 0x3039
inc   rsi
```

Байт ксорится с младшим байтом состояния, состояние крутится LCG (константы как у классического `rand()`). В состояние подмешивается исходный зашифрованный байт, поэтому ключевой поток зависит от самих данных.

Даже после расшифровки статически это читать тяжело: после jmp идет мусор, есть opaque predicates, константы собираются из нескольких инструкций.

Дальше запускается регистровая VM. Что удалось понять:

- `RBX` хранит виртуальный IP;
- `R13` указывает на массив виртуальных регистров, примерно `0x430` байт;
- в `R14` сохраняются флаги гостя;
- диспетчер (около `0x406291`) читает опкод через `movzx eax, byte ptr [rbx]`, сдвигает `RBX` и выбирает хендлер длинной цепочкой `cmp`/`jne`, таблицы нет;
- условные переходы восстанавливают сохраненные флаги и по ним считают новый `RBX`.

Разбирать все опкоды я не стал. Хватило логировать в каждом хендлере только чтения и записи в виртуальные регистры (`read v[n]` / `write v[n]`). Вся нативная обфускация из такой трассы пропадает, и остается чистый dataflow.

## Длина пароля

Погонял эмулятор с разными длинами аргумента и посчитал чтения из буфера `argv[1]`:

```text
len=10  input reads=0
len=11  input reads=12
len=12  input reads=0
```

На живом бинаре то же самое:

```bash
$ ./ShouldBeNormal wolffmumif
bad password.

$ ./ShouldBeNormal wolffmumifyy
bad password.
```

При длине 11 VM читает смещения 0..11, то есть 11 символов плюс завершающий ноль. Ноль нужен только чтобы остановить цикл, в хеш он не идет. Значит, строкового сравнения нет, ищем функцию, которая сворачивает 11 байт в число.

## Сравнение

`bad password.` лежит в `.rodata` по `0x402022`. Нашел момент, когда этот адрес попадает в регистр VM, и пошел по dataflow назад. Вышел на такой хендлер:

```asm
0x40f749: mov    eax, dword ptr [rcx]   ; вычисленное значение, VM-регистр 2
0x40f753: mov    edx, dword ptr [rbx]   ; константа из bytecode
0x40f75b: add    rbx, 4
0x40f768: cmp    eax, edx
0x40f772: pushfq
0x40f7a1: pop    r14
```

Константа в байткоде:

```text
0x7C7652D1
```

И это вся проверка: хеш должен быть равен `0x7C7652D1`.

Поставил хук на `0x40f768` и посмотрел, что приходит для разных входов:

```text
ABCDEFGHIJK  -> 0x17e23b74
AAAAAAAAAAA  -> 0x495678c4
BAAAAAAAAAA  -> 0xfcd1c7a1
target       -> 0x7c7652d1
```

Сравнивается одно 32-битное число целиком, не по символам, так что посимвольный подбор по таймингу или по трассе не сработает: до `cmp` все входы идут одним путем.

## Хеш

По трассе на каждый символ `c` с аккумулятором `h` делается следующее. Сначала три операции:

```text
h | c
h & c
(h | c) - (h & c)
```

Но `(h | c) - (h & c)` это ровно `h ^ c`, обфускатор просто расписал XOR подлиннее.

Потом:

```text
h *= 0x045D9F3B
h = rol32(h, 7)
h += 0x01234567
```

Все по модулю 2^32. Начальное значение собирается из двух половинок, в итоге `0xC001D00D` (cool dude, ага).

На питоне:

```python
MASK = 0xffffffff

def rol32(x, n):
    return ((x << n) | (x >> (32 - n))) & MASK

def digest(password):
    h = 0xc001d00d
    for c in password.encode():
        h ^= c
        h = (h * 0x045d9f3b) & MASK
        h = rol32(h, 7)
        h = (h + 0x01234567) & MASK
    return h
```

Сверяем с тем, что видели в эмуляторе:

```text
digest("ABCDEFGHIJK") = 0x17e23b74
digest("AAAAAAAAAAA") = 0x495678c4
digest("BAAAAAAAAAA") = 0xfcd1c7a1
digest("wolffmumify") = 0x7c7652d1
digest("transrights") = 0x7c7652d1
```

Последние две строки оригинальный бинарь тоже принимает.

## Кейген

Раунд выглядит как

```text
h_next = F(h_prev ^ c)
```

где

```text
F(x) = rol32(x * 0x045D9F3B, 7) + 0x01234567
```

И `F` обращается: множитель нечетный, значит у него есть обратный по модулю 2^32; rol откатывается через ror, сложение через вычитание, XOR с известным байтом через тот же XOR.

```python
def Finv(y):
    x = (y - ADD) & MASK
    x = ror32(x, 7)
    x = (x * MULINV) & MASK
    return x
```

Для 11 символов я сделал meet-in-the-middle: фиксирую первые 4 символа, перебираю последние 4 назад от таргета и складываю состояния в словарь, потом перебираю 3 средних вперед и ищу совпадение. На один префикс это примерно 26^4 + 26^3 операций, то есть мгновенно.

Скрипт лежит рядом: [keygen.py](./keygen.py).

```bash
$ python3 keygen.py
wolffmumify
treelyinbke
wishswaftip
snowtocdfjh
```

Проверка:

```bash
$ ./ShouldBeNormal wolffmumify
good job!

$ ./ShouldBeNormal treelyinbke
good job!

$ ./ShouldBeNormal wishswaftip
good job!

$ ./ShouldBeNormal snowtocdfjh
good job!

$ ./ShouldBeNormal transrights

```

## Ответ

Пароль автора: `transrights`. Мой сгенерированный: `wolffmumify`.

Валидных ключей много, потому что проверяется только 32-битный хеш, а 11-символьных строк из printable ASCII куда больше, чем 2^32, так что коллизии неизбежны. Для крякми любая из них подходит, но "настоящий" ответ все-таки `transrights`.
